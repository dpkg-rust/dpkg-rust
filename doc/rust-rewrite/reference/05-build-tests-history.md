## A. Build system

### A.1 Bootstrap and version derivation
- `autogen` (`autogen:1-9`): sets `git config blame.ignoreRevsFile` when in git, then runs `autoreconf --force --install`. That is the only bootstrap step.
- **Tracked vs generated.** Only 11 dpkg-specific macros are tracked in `m4/` (`m4/dpkg-{arch,build,compiler,coverage,funcs,headers,libs,linker,progs,types,unicode}.m4`, 1,626 lines in total). All other `m4/*.m4` files (libtool, gettext, nls, po, iconv, …) are copied in by autoreconf/autopoint; `m4/.gitignore` ignores `*.m4` except `dpkg-*.m4`. The tracked `build-aux/` files are `autotest.am cpan.am gen-changelog gen-release get-make-jobs get-vcs-id get-version lcov-inject run-script subst.am tap.am test-runner`. `compile config.guess config.sub depcomp install-sh ltmain.sh missing ar-lib config.rpath` are generated (`git ls-files m4 build-aux`; `git status --ignored`).
- **Version** (`configure.ac:6`): `AC_INIT([dpkg], m4_esyscmd([build-aux/get-version]), …)`.
  - `build-aux/get-version:27-44` uses `.dist-version` in tarballs. Otherwise it runs `git describe --abbrev=4 HEAD | tr %_ :~`, because tags cannot contain `:`/`~`, and appends `-dirty` if the tree is dirty.
  - `build-aux/get-vcs-id` works the same way and yields the commit hash.
  - `DPKG_DIST_IS_RELEASE` (`m4/dpkg-build.m4:91-100`) counts a version as a "release" if it contains no `-`. That flag controls the CPAN `-TRIAL` suffix (`build-aux/cpan.am:3-5`).
  - `DPKG_BUILD_RELEASE_DATE` (`m4/dpkg-build.m4:14-19`) **runs the in-tree Perl `scripts/dpkg-parsechangelog.pl`** on `debian/changelog` to obtain the release date.
- `make dist` (`Makefile.am:252-270`) writes `.dist-version`, `.dist-vcs-url` and `.dist-vcs-id` into the tarball. When building from git it **fails if any git-tracked file is missing from the dist tarball**, or if any symlink other than `t/origins/default` is tracked, and it generates `ChangeLog` from `git log -C --stat 1.15.0..`. Tarballs are ustar, xz only (`configure.ac:23-30`: `tar-ustar no-dist-gzip dist-xz`), with `TAR_OPTIONS=--owner=0 --group=0` (`Makefile.am:241-242`).

### A.2 Automake/libtool options
- `AM_INIT_AUTOMAKE([1.11] [-Wall] [foreign] [nostdinc] [subdir-objects] [tar-ustar no-dist-gzip dist-xz])` (`configure.ac:23-30`); silent rules are on (`:31`).
- `m4_pattern_forbid([^_?DPKG_])` (`configure.ac:3`), so any unexpanded `DPKG_*` macro is fatal.
- **libtool, static only.** `LT_INIT([disable-shared])` (`configure.ac:48`). The comment at `configure.ac:43-46` explains that shared libraries are disabled on purpose because there is no ABI stability guarantee. `DPKG_BUILD_SHARED_LIBS` (`m4/dpkg-build.m4:6-10`) **errors out on `--enable-shared` unless `AUTHOR_TESTING` is set**; GitLab CI's `shlib-tests` job exercises exactly that path (`.gitlab-ci.yml:61-66`).
- `DPKG_LINKER_AS_NEEDED` and `DPKG_LINKER_VERSION_SCRIPT` (`m4/dpkg-linker.m4:29-69`) only define AM conditionals.
  - `--as-needed` is applied only in `dselect/Makefile.am:19-23`.
  - The version script `lib/dpkg/libdpkg.map` (428 `;`-terminated lines, `LIBDPKG_0 { global: … }`) is applied to `libdpkg.la` (`lib/dpkg/Makefile.am:36-48`). When version scripts are unsupported, the fallback is `-export-symbols libdpkg.sym`, generated by sed from the map (`:210-216`).
  - In practice this only matters if the shared library is ever enabled.
- **Nothing is fully static.** The only static linking is of dpkg's own `libdpkg.a`/`libcompat`; no `-static` or `-all-static` appears anywhere (grep over `Makefile.am`, `m4`, `configure.ac`, `debian/rules`). The exception is that `--with-libX=static` on the compression libraries emits `-Wl,-Bstatic -lX -Wl,-Bdynamic` (`m4/dpkg-libs.m4:49-50`).

### A.6 Compiler and linker flag policy (actual values in this build)
From `build/Makefile`:
- **`CFLAGS`**: `-fstrict-flex-arrays=3 -fcf-protection=full -fstack-clash-protection -fstack-protector-strong`, then about 45 `-W…` flags, then `-g -O2`.
  - The dialect and hardening flags appear 2–3 times. Each `DPKG_COMPILER_*` macro re-prepends the cumulative `$DPKG_COMPILER_CFLAGS` (`dpkg-compiler.m4:67,97,219`). This is harmless but noisy.
- **`LDFLAGS`**: `-Wl,-O1`.
- **No LTO, PIE, RELRO, bindnow or `_FORTIFY_SOURCE` from upstream configure.** I grepped `configure.ac`, `m4/dpkg-*.m4`, all `Makefile.am` and `debian/rules` for `flto`, `FORTIFY`, `relro`, `-pie` and `fPIE`; the only hits are the `data/*pie*.specs` files shipped for dpkg-buildflags.
  - In the Debian package those flags come from the **in-tree** `dpkg-buildflags` with `DEB_BUILD_MAINT_OPTIONS = hardening=+all` (`debian/rules:13-22,52`).
  - `scripts/Dpkg/Vendor/Debian.pm:154-175` defines the hardening feature set (pie, stackprotector{,strong}, stackclash, fortify, format, relro, bindnow, branch). LTO is a feature with default `lto => 0` (`:146`; flags at `:545-546`).
- Ubuntu's gcc here defaults to PIE (`gcc -v` shows `--enable-default-pie`), and its specs pass `--as-needed`.
  - The binaries import `__*_chk` symbols (e.g. `nm -u utils/update-alternatives`), i.e. fortify is active through the distro compiler defaults, not dpkg's configure.
  - On a toolchain without default `--as-needed`, every `libdpkg` consumer would pick up all of `-lz -llzma -lzstd -lbz2 -lmd`, which come from `dependency_libs` in `build/lib/dpkg/libdpkg.la`. **(inferred)**

## B. Test infrastructure

### B.0 Harness plumbing
- **TAP suites** use `build-aux/tap.am`. `tap-check` (`:18-35`) exports `TEST_PARALLEL`, `TEST_VERBOSE`, `abs_*dir`, `CC`, `PERL`, `PERL_DL_NONLAZY=1` and `PERL5OPT=$(TEST_COVERAGE)`, then runs `perl build-aux/test-runner <programs> <scripts>`.
  - `build-aux/test-runner` (Perl `TAP::Harness`) sets `LC_ALL=C` and `DPKG_COLORS=never`, and **prepends `$builddir/src:scripts:utils` to `PATH`** (`:11-13`).
  - It **executes any non-`.t` executable directly as a TAP producer**, and `.t` files via perl (`:24-27`), with `lib => [scripts, dselect/methods]` (`:29-32`).
  - `authorcheck` = `AUTHOR_TESTING=1 make check` (`tap.am:37-38`).
  - Parallelism: `build-aux/get-make-jobs` parses `-jN` from `MAKEFLAGS` (it is a Perl script using `Dpkg::SysInfo`).
- **Autotest** uses `build-aux/autotest.am`. `autotest-check` runs `$(SHELL) src/at/testsuite -C at -j$(TEST_PARALLEL)` (`:28-29`). `autotest-installcheck` runs the same with `AUTOTEST_PATH=$(bindir)` (`:31-32`), so `make installcheck` runs the autotest suite against the installed binaries.
- **Not Automake's parallel test driver.** There is no `TESTS =`/`test-suite.log`; each directory has `check-local: tap-check` or `autotest-check`.

## I. Facts relevant to adding Rust to this build

**Hook points in the Makefile tree:**
- **Build order.** Top-level `SUBDIRS = lib src utils [dselect] scripts po man` (`Makefile.am:7-15`), and `lib/SUBDIRS = compat dpkg` (`lib/Makefile.am:3-6`). Anything consumed by `src`/`utils` must be built in or before `lib`, or in the same directory.
- **Library-level hook.** `libdpkg_la_LIBADD` (`lib/dpkg/Makefile.am:50-59`) is what every C program inherits through `LDADD = ../lib/dpkg/libdpkg.la` (`src/Makefile.am:11-15`, `dselect/Makefile.am:53-58`, the unit tests at `lib/dpkg/Makefile.am:14-18`).
  - But `libdpkg.a` is **installed and shipped** in `libdpkg-dev` (`debian/libdpkg-dev.install:3`) with `libdpkg.pc` `Libs.private: @PS_LIBS@ @MD_LIBS@ @Z_LIBS@ @LZMA_LIBS@ @ZSTD_LIBS@ @BZ2_LIBS@` (`lib/dpkg/libdpkg.pc.in:13`). Any Rust archive or extra system library that libdpkg needs would surface to external consumers there.
  - `libcompat.la` is already absorbed into `libdpkg.a` as a libtool convenience library (changelog: "Use libtool to build the static libraries, which makes it possible to embed libcompat inside libdpkg", `debian/changelog:7756-7757`). Whether libtool would absorb a non-libtool Rust `.a` the same way is **unverified**.
- **Program-level hook.** Per-program `*_LDADD` (`src/Makefile.am:87-90,131-134`; `utils/Makefile.am:35-38,75-80`). `update-alternatives` and `start-stop-daemon` link only libcompat and could be replaced as whole programs without touching libdpkg. `bin_PROGRAMS`/`sbin_PROGRAMS` lists are in `src/Makefile.am:25-34` and `utils/Makefile.am:14-85`.
- **Compile-time paths.** Configuration reaches C as `-D` defines in `AM_CPPFLAGS` (`ADMINDIR`, `LOCALEDIR`, `CONFIGDIR`, `LOGDIR`, `SYSCONFDIR`, `RUNSTATEDIR`, `LIBDIR`: `lib/dpkg/Makefile.am:3-11`, `src/Makefile.am:3-10`, `utils/Makefile.am:3-12`, `dselect/Makefile.am:5-14`) and through `config.h` (`configure.ac:284`; e.g. `ARCHITECTURE`, `DPKG_DEFAULT_SHELL`, `BUILD_*`, `WITH_LIB*`, `DEB_DEFAULT_COMPRESSOR`). A Rust component would need an equivalent channel (env vars to a build script, or generated `.rs`).
- **Precedents for custom generation rules** in automake: `dselect/Makefile.am:74-79` (cpp + Perl generator) and `utils/Makefile.am:53-57` (msgfmt + Perl). There is no automake-native Rust support in the tree.

**Automake/libtool machinery to coexist with:**
- **dist / distcheck.**
  - `dist-hook` aborts if any git-tracked file is not in the tarball (`Makefile.am:262-267`), so every committed Rust file (`Cargo.toml`, `Cargo.lock`, sources, any `vendor/`) must be listed in `EXTRA_DIST` or a `dist_*` variable.
  - Tracked symlinks are forbidden except `t/origins/default` (`:257-261`).
  - `tests/` is shipped wholesale (`:215-219`).
  - GitLab runs `make distcheck` (`.gitlab-ci.yml:13-17`). In distcheck automake builds VPATH from a read-only srcdir (standard automake behaviour, **unverified here**), so any cargo target/lock writes must go to builddir.
- **Out-of-tree builds** are standard here (A.9). Autotest already writes `src/at/testsuite` into srcdir (A.3).
- **`make check` TAP driver.** `build-aux/test-runner:24-27` executes any non-`.t` executable as a TAP producer, so a Rust test binary that emits TAP could be added to a directory's `test_programs` the same way C tests are (`lib/dpkg/Makefile.am:227-264,309-316`). `cargo test` output is not TAP.
  - The black-box suites (`src/at` via PATH/`AUTOTEST_PATH`, `tests/` via PATH, `utils/t` via `$builddir/update-alternatives`) need no change to exercise a binary with the same name and CLI.
- **Cross-compilation.**
  - configure derives the Debian arch from `$host` via the Perl `dpkg-architecture.pl -t$host` (`m4/dpkg-arch.m4:12`), and has cross-safe fallbacks for `AC_RUN_IFELSE` checks (`m4/dpkg-funcs.m4:55-71,115-133`).
  - GNU names in `data/cputable` (column 2: `x86_64`, `i686`, `aarch64`, `arm`, `powerpc64le`, …) and the ostable GNU systems (`linux-gnueabihf`, …) are GNU triplets, not Rust target triples. A mapping layer would be needed.
  - `rustc --print target-list` on this host lists 322 targets; installed rustup targets are `x86_64-unknown-linux-gnu`, `x86_64-unknown-linux-musl` and `x86_64-pc-windows-gnu`.
- **`DEB_BUILD_OPTIONS`** handled in `debian/rules`: `terse` (`:28-30`), `parallel=N` → `TEST_PARALLEL` (`:32-37`); `nocheck` via dh and the `<!nocheck>` Build-Depends. Build flags come only from the in-tree `dpkg-buildflags --export=configure` (`:52`), which emits C/C++/LD flags and **no RUSTFLAGS** (H.6).
- **`debian/control` changes needed:**
  - There is currently no rustc/cargo in Build-Depends (`:10-64`).
  - `dpkg` has `Pre-Depends: ${shlibs:Depends}` (`:70-71`), so any new shared-library dependency of the Essential binaries becomes a Pre-Depends.
  - `source/format` is `3.0 (native)` (`debian/source/format`), so vendored crates would sit in the native tarball.
  - How Debian packages Rust crates (`librust-*-dev`, dh-cargo) is general knowledge, not evidenced in this tree **(unverified here)**.
