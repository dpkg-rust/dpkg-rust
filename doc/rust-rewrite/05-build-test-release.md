# 05 — Build system, tests, packaging and project history

How dpkg is built, tested, packaged and released, plus what the git history says about
where bugs and effort go.

Line-level detail and citations:
[reference/05-build-tests-history.md](reference/05-build-tests-history.md).

## 1. Build system

dpkg uses autoconf, automake and libtool.

```
./autogen                 # autoreconf --force --install
mkdir build-tree && cd build-tree
../configure              # out-of-tree builds are the normal case
make
make check
```

### 1.1 Hard and optional requirements

| Required (configure fails without it) | Optional |
|---|---|
| C99 compiler | zlib or zlib-ng, liblzma, libzstd, libbz2 (otherwise the command-line tools are used) |
| **C++14 compiler**, even with `--disable-dselect`, because the headers are tested as C++ | libselinux (Linux) |
| **perl ≥ 5.36**: configure runs in-tree Perl scripts | gettext (translations) |
| GNU tar and GNU patch | curses (only for dselect) |
| MD5 functions, from libc or libmd | po4a, pod2man, doxygen |
| pkg-config macros at autoreconf time | lcov and Devel::Cover (coverage) |

Two configure steps run the in-tree Perl tools: `scripts/dpkg-architecture.pl -t$host`
computes the Debian architecture compiled into the C programs, and
`scripts/dpkg-parsechangelog.pl` supplies the release date. The version comes from
`git describe` (or `.dist-version` in a tarball).

### 1.2 Layout of the build

Top-level order: `lib` → `src` → `utils` → `dselect` (optional) → `scripts` → `po` → `man`.

| Directory | Product |
|---|---|
| `lib/compat` | `libcompat` convenience library, folded into libdpkg |
| `lib/dpkg` | static `libdpkg.a`, 52 installed headers, `libdpkg.pc`, 37 unit-test programs |
| `src` | the eight C programs, three shell scripts (generated by substitution), the autotest suite |
| `utils` | `update-alternatives`, `start-stop-daemon` (each can be disabled) |
| `dselect` | the C++ front-end and its access methods |
| `scripts` | Perl modules and programs, make fragments, Perl tests |
| `po`, `man` | message catalogs; manual pages from POD |

Only dpkg's own libraries are linked statically; system libraries are dynamic.

### 1.3 Flags

`configure` adds about 45 warning flags, `-fstrict-flex-arrays=3` and a few hardening flags
(`-fstack-protector-strong`, `-fstack-clash-protection`, `-fcf-protection`). It does not
add LTO, PIE or `_FORTIFY_SOURCE`; the Debian package gets those from the in-tree
`dpkg-buildflags` with `hardening=+all`. `--enable-compiler-sanitizer` turns on ASan and
UBSan. `--enable-coverage` enables gcov, lcov and Devel::Cover.

### 1.4 Distribution rules that affect contributors

`make dist` fails if any git-tracked file is missing from the tarball, and if any symlink
other than `t/origins/default` is tracked. Every new file therefore has to be listed in a
`Makefile.am`. The whole `tests/` tree is shipped through `EXTRA_DIST`.

## 2. Test suites

There are six kinds of tests. Results below are from a run on the analysis machine.

| Suite | Location | Kind | Size | Result | In `make check` |
|---|---|---|---|---|---|
| C unit tests | `lib/dpkg/t/` | white-box: links libdpkg | 40 files, 3,989 assertions | all pass | yes |
| Autotest | `src/at/*.at` | **black-box**: runs programs by name, inspects files | 80 groups | all pass | yes |
| Perl tests | `scripts/t/` | 46 files import modules; 5 run programs | 51 files, 12,745 assertions | pass, 15 skipped | yes |
| update-alternatives | `utils/t/` | **black-box** | 712 assertions | all pass | yes |
| Lint and author tests | `t/` | source checks (POD, syntax, critic, spelling, shellcheck, cppcheck) | 14 files | 3 ran (485 assertions), 11 skipped | yes; most need `AUTHOR_TESTING=1` |
| Functional suite | `tests/` | **black-box**: builds packages, drives `dpkg` | 89 scenario directories | 81 pass in 23 s as a normal user | **no** |

`make check` took 11.8 s with the test programs already compiled.

### 2.1 How the suites find the code under test

This matters for anyone validating a reimplementation.

- **Autotest** puts `<builddir>/src` first in `PATH`. `make installcheck` runs the same suite
  against the installed binaries through `AUTOTEST_PATH`.
- **The functional suite** prepends `$(DPKG_BUILDTREE)/{src,utils,scripts}` to `PATH`, or uses
  the system `PATH` with `make installtest`. It invokes `dpkg`, `dpkg-deb`, `dpkg-query`,
  `dpkg-divert`, `dpkg-split` and `dpkg-trigger` by bare name.
- **`utils/t`** runs `$builddir/update-alternatives`.
- The TAP runner (`build-aux/test-runner`) executes any non-`.t` executable as a test
  program, so a test binary in any language that prints TAP can be added.

A drop-in replacement placed first in `PATH` is therefore exercised by the autotest and
functional suites with no change to the tests.

### 2.2 The functional suite

Each directory under `tests/` holds package trees (`pkg-*/DEBIAN/control` plus scripts and
payload) and a `Makefile` with a `test-case` rule. The framework builds the `.deb` files
with `dpkg-deb`, runs `dpkg` commands, and asserts on package states, files and output.

It does not need root. By default it installs into a private directory with
`--force-not-root --force-script-chrootless` and a private admin directory. Only
`t-unpack-device` needs root (it creates device nodes).

By theme: conffiles 21, unpack and filesystem objects 18, package relationships 15,
triggers 11, file ownership 9, options and miscellany 7, database and control parsing 5,
maintainer scripts 3. Three scenarios are listed as known failures and two as manual.

The suite was a separate repository until 2021, and `tests/README` says the plan is to
migrate it into the autotest suite. It is run by upstream's GitLab CI and by the Debian
autopkgtests, but not by `make check` and not by this fork's GitHub workflow.

### 2.3 Gaps

- `start-stop-daemon` and `dselect` have no tests.
- The deb822 parser, the status journal, triggers and compression have no unit tests;
  they are covered only through the program-level suites.
- There are no fuzzing harnesses in the tree. Three fixes from 2015 are credited to AFL.
- Coverage tooling exists but is not part of any routine run.

## 3. Continuous integration

**This fork** (`.github/workflows/build.yml`): install build dependencies, `./autogen`,
out-of-tree configure, `make`, `make check`. It does not run the functional suite, author
tests, `distcheck` or a sanitizer build. Its failure step looks for `test-suite.log`, which
this project never produces (autotest writes `src/at/testsuite.log`).

**Upstream** (`.gitlab-ci.yml`, Debian sid): `distcheck`; author checks; unit tests under
ASan and UBSan; an out-of-tree build; a build with every optional library disabled; a
shared-library build; and the functional suite under the sanitizers.

**Debian autopkgtest** (`debian/tests/`): the autotest suite against the installed
binaries, and the functional suite, each as root and as a normal user.

## 4. Debian packaging

| Package | Architecture | Notes |
|---|---|---|
| `dpkg` | any | **Essential: yes.** `Pre-Depends: ${shlibs:Depends}`. The C programs, `update-alternatives`, `start-stop-daemon`, shell helpers, architecture tables. No Perl |
| `libdpkg-dev` | any | `libdpkg.a`, headers, `libdpkg.pc`, autoconf macros |
| `dpkg-dev` | all | The 19 Perl programs and the make fragments. Depends on perl, `libdpkg-perl`, bzip2, xz-utils, patch, make, binutils |
| `libdpkg-perl` | all | The `Dpkg::*` modules |
| `dselect` | any | The curses front-end |

Because `dpkg` is Essential and uses `Pre-Depends`, every shared library it links becomes a
pre-dependency of the base system. The source package format is `3.0 (native)`.

Bootstrapping facts: building dpkg needs a C and C++ compiler, perl, GNU tar, GNU patch,
libmd, debhelper and po4a. Installing packages needs only the `dpkg` binary package. dpkg
is also what installs the compilers and perl in the first place, so new architectures
bootstrap it by cross-compilation.

## 5. Architecture coverage

`data/cputable` knows 34 CPUs and `data/ostable` 20 system types; together with
`data/tupletable` they yield 201 Debian architecture names.

- **CPUs**: alpha, amd64, arc, arm, arm64, armeb, hppa, i386, ia64, loong64, m68k, eight
  MIPS variants, nios2, or1k, powerpc, powerpcel, ppc64, ppc64el, riscv64, s390, s390x,
  sh3, sh3eb, sh4, sh4eb, sparc, sparc64.
- **Systems**: Linux with glibc, musl and uClibc (and the ARM, MIPS, x32 and SPE ABI
  variants), Hurd, FreeBSD, NetBSD, OpenBSD, DragonFly, Darwin, Solaris, AIX, MiNT.

The C code itself carries per-OS branches for Linux, Hurd, the BSDs, macOS, Solaris, AIX and
HP-UX, and `lib/compat/` fills in missing libc functions. Portability beyond Linux is an
explicit goal of the code base.

## 6. What the history says

The repository has 13,627 commits since 1996.

### 6.1 Security history

Fourteen CVE identifiers appear in commit messages and the Debian changelog.

| Component | CVEs | Classes |
|---|---|---|
| Perl (`dpkg-source` and its modules) | 10 | 8 path traversal through crafted patches or archives; 1 signature-parsing logic error; 1 module-search-path injection |
| C | 4 | 1 memory-safety bug (an off-by-one write in `dpkg-deb`, found by fuzzing in 2015); 1 format-string injection (2014); 2 denial of service (2025, 2026) |

Most of dpkg's security history is in Perl and is about paths, not memory.

### 6.2 Memory-safety fixes, last ten years

A keyword search over 4,301 commits since October 2016, classified by hand from the commit
messages, found 70 commits fixing memory-safety-type bugs (1.6 %):

| Class | Commits |
|---|---|
| User-facing crashes, overflows, use-after-free | 9 |
| Found by developer review | 10 |
| Found by AddressSanitizer or UBSan (mostly short-lived leaks; 17 in a 2020 campaign) | 22 |
| Static-analyser clean-ups (Coverity, cppcheck, compiler warnings) | 29 |

By area: libdpkg 36, `src/` 23, `utils/` 11, dselect 3, Perl 0. The classification read
commit messages only, not diffs, and a keyword search can miss fixes.

### 6.3 Where the work goes

Commits per year touching each area (2022–2025 average): `scripts/` about 190, `man/` about
100, `lib/` about 70, `src/` about 60, `dselect/` about 55, `utils/` about 17.

The most frequently changed code files of the last five years are
`scripts/dpkg-buildpackage.pl` (82 commits), `utils/start-stop-daemon.c` (63),
`scripts/Dpkg/Vendor/Debian.pm` (62), `utils/update-alternatives.c` (54),
`scripts/dpkg-shlibdeps.pl` (51) and `scripts/dpkg-source.pl` (50). Of the thirty most
changed non-translation files, thirteen are Perl and six are C or C++.

### 6.4 Contributors

| Period | Commits | Share by the top author |
|---|---|---|
| 2018–2026, all commits | 3,675 | 88.7 % (Guillem Jover) |
| 2018–2026, excluding translation-only commits | 3,106 | 96.7 % |

Development is active (roughly 400 to 570 commits a year) and almost entirely the work of
one maintainer. A new major series appears about every two years (1.21.0 in December
2021, 1.22.0 in August 2023, 1.23.0 in December 2025).

### 6.5 Language migrations that already happened here

| Program | Change | Year |
|---|---|---|
| `dpkg-statoverride` | Perl → C | 2009 |
| `update-alternatives` | Perl → C | 2010 |
| `dpkg-divert` | Perl → C | 2010 |
| `dpkg-split` helper (`mksplit`) | Perl → C | 2010 |
| `dpkg-realpath` | shell → C | 2024 |

All were done one program at a time. Nothing in the tree mentions Rust, apart from the
language-neutral `Static-Built-Using` control field added in 2022, and the in-tree
`dpkg-buildflags` emits no Rust flags.
